Debugging an ST75160i LCD Migration

By John Glatts

I recently started working with the newer revision of the NHD-C160100DiZ-FSW-FBW LCD from Newhaven Display. At first glance, the module looked nearly identical to previous versions I had worked with, so I assumed my existing ST7528i driver would work with minimal changes.

It did not.

Initial Symptoms

The display would power correctly and eventually ACK over I2C, but the screen only showed random pixels and corrupted output. Initially, I suspected:

  • Incorrect pullups
  • Voltage level mismatch
  • Bad framebuffer packing
  • Broken display glass
  • Reset timing issues

The first major clue was that the display would not ACK at all until a proper hardware reset pulse was added. 

digitalWrite(rst, LOW);
```

delay(20);

digitalWrite(rst, HIGH);
delay(200);
```

5V vs 3.3V Problems

I initially tested the display using an Arduino Mega. This turned into a rabbit hole pretty quickly.

The Mega's I2C lines were being pulled up to 5V, which caused the supposedly 3.3V bus to float above 4V. The display would not reliably ACK and the bus behavior was inconsistent.

The ESP32 ended up being a much better fit for this display due to native 3.3V logic support.

The Real Problem

After digging through the Newhaven documentation, I found the actual issue: 

ST7528i -> ST75160i

The newer Rev1C modules use an entirely different controller. Even though the displays look nearly identical, the initialization sequence and RAM format are different.

Once I loaded the proper ST75160i initialization sequence from the datasheet, the display finally came alive.

Good Signs During Bring-Up

One interesting thing during debugging: random pixels on the screen were actually a good sign.

That confirmed:

  • LCD glass was alive
  • Booster circuit was working
  • Contrast voltage was functioning
  • RAM writes were occurring
  • Addressing was partially correct

The remaining issue ended up being framebuffer packing and RAM addressing differences between the two controllers.

Framebuffer Differences

The original ST7528i implementation used a different page and grayscale memory layout. The ST75160i framebuffer format packs 4 vertical pixels into a single byte: 

0x80 = row 0
```

0x40 = row 1
0x20 = row 2
0x10 = row 3
```

Once the framebuffer logic was updated to match the new controller, rendering started behaving correctly.

Takeaways

This was a good reminder that "compatible" display revisions are not always firmware compatible. Even a seemingly minor controller revision can completely change:

  • Initialization sequence
  • Voltage setup
  • Framebuffer packing
  • RAM addressing
  • Power sequencing

Always check the transition guides and updated datasheets before assuming an LCD module is a drop-in replacement.
