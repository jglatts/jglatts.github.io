Building a Wi-Fi Photo Frame with an ESP32

July 2026 • ESP32 • Embedded Systems • Graphics • JavaScript

This project started as a simple test for a small 240×240 ST7789 TFT display. Initially I was converting photos into C header files and compiling them directly into the firmware. It worked, but every time I wanted to display a new image I had to regenerate the bitmap and upload new firmware.

That quickly became tedious, so I decided to build a tiny web application that lets anyone upload a picture from their browser directly to the display over Wi-Fi.

The Hardware

The project uses an ESP32 driving a 240×240 ST7789 IPS TFT over SPI. The ESP32 also hosts a lightweight web server which serves a simple HTML page.

The goal was simple:
  • No firmware updates required for new pictures.
  • Upload directly from a phone or computer.
  • Automatically crop and resize images.
  • Display immediately.

The Browser Does the Heavy Lifting

Instead of asking the ESP32 to decode JPEG images, the browser performs all of the expensive work. Using an HTML canvas, the selected image is:

  • Loaded into memory
  • Center cropped into a square
  • Resized to 240×240
  • Converted from RGB888 into RGB565

Once converted, the browser sends the pixel data directly to the ESP32.

Why RGB565?

Computer images normally use 24-bit RGB: 


8 bits Red
8 bits Green
8 bits Blue

24 bits total

The ST7789 display instead expects RGB565: 


RRRRRGGGGGGBBBBB

5 bits Red
6 bits Green
5 bits Blue

Converting colors in JavaScript dramatically reduces the amount of processing required on the ESP32.

Streaming the Image

Rather than uploading the entire image at once, the browser streams one horizontal scanline at a time. Each row contains: 


240 pixels

×

2 bytes per pixel

=

480 bytes

The ESP32 reconstructs that single line and immediately draws it to the display. 


Browser

Row 0  ─────────────► ESP32 ─► TFT

Row 1  ─────────────► ESP32 ─► TFT

Row 2  ─────────────► ESP32 ─► TFT

...

Row239 ─────────────► ESP32 ─► TFT

Minimal Memory Usage

One of the neat aspects of this design is that the ESP32 never stores the full image. Instead, it only needs enough RAM for a single scanline: 


240 pixels

×

2 bytes

=

480 byte buffer

A complete 240×240 image would require over 115 KB of RAM, while this implementation only needs a 480 byte working buffer.

Handling Chunked HTTP Uploads

One thing I learned while building this project is that an HTTP upload isn't guaranteed to arrive all at once. A 480 byte scanline might arrive as several smaller packets: 


Chunk 1
128 bytes

Chunk 2
128 bytes

Chunk 3
128 bytes

Chunk 4
96 bytes

The web server callback provides the current offset and total size so the firmware can reconstruct the complete scanline before sending it to the display. Once the line has been drawn, the same buffer is reused for the next row.

What's Next?

  • Store images in flash memory
  • Create an image gallery
  • Automatic slideshow mode
  • Touchscreen support
  • JPEG decoding directly on the ESP32
  • OTA firmware updates from the same web interface
This started as a display demo, but quickly became a fun project combining embedded firmware, web development, networking, graphics processing, and a bit of computer science. It's a great example of how small side projects often grow into something much more interesting than originally planned.
