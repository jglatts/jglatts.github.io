Building a Wi-Fi Photo Frame with an ESP32

This project started as a simple test for a small 240×240 ST7789 TFT display. Initially I was converting photos into C header files and compiling them directly into the firmware. It worked, but every time I wanted to display a new image I had to regenerate the bitmap and upload new firmware.

That quickly became tedious, so I decided to build a tiny web application that lets anyone upload a picture from their browser directly to the display over Wi-Fi.

The Hardware

The project uses an ESP32 driving a 240×240 ST7789 IPS TFT over SPI. The ESP32 also hosts a lightweight web server which serves a simple HTML page.

The goal was simple:
  • No firmware updates required for new pictures.
  • Upload directly from a phone or computer.
  • Automatically crop and resize images.
  • Display immediately.

The Browser Does the Heavy Lifting

Instead of asking the ESP32 to decode JPEG images, the browser performs all of the expensive work. Using an HTML canvas, the selected image is:

  • Loaded into memory
  • Center cropped into a square
  • Resized to 240×240
  • Converted from RGB888 into RGB565

Once converted, the browser sends the pixel data directly to the ESP32.

Why RGB565?

Computer images normally use 24-bit RGB: 


8 bits Red
8 bits Green
8 bits Blue

24 bits total

The ST7789 display instead expects RGB565: 


RRRRRGGGGGGBBBBB

5 bits Red
6 bits Green
5 bits Blue

Converting colors in JavaScript dramatically reduces the amount of processing required on the ESP32.

Streaming the Image

Rather than uploading the entire image at once, the browser streams one horizontal scanline at a time. Each row contains: 


240 pixels

×

2 bytes per pixel

=

480 bytes

The ESP32 reconstructs that single line and immediately draws it to the display. 


Browser

Minimal Memory Usage

One of the neat aspects of this design is that the ESP32 never stores the full image. Instead, it only needs enough RAM for a single scanline: 


240 pixels

×

2 bytes

=

480 byte buffer

The Browser Upload Loop

The browser reads the resized canvas pixel data, converts each pixel from RGB888 into RGB565, and sends one 480 byte scanline at a time to the ESP32. 


async function upload(){
  const imgData = ctx.getImageData(0,0,240,240).data;
  statusText.innerText = "Uploading...";

  for(let y = 0; y < 240; y++){
    const out = new Uint8Array(480);

    for(let x = 0; x < 240; x++){
      const i = ((y * 240) + x) * 4;

      const r = imgData[i] >> 3;
      const g = imgData[i + 1] >> 2;
      const b = imgData[i + 2] >> 3;

      const rgb565 = (r << 11) | (g << 5) | b;

      out[x * 2] = rgb565 >> 8;
      out[x * 2 + 1] = rgb565 & 255;
    }

    await fetch("/line?y=" + y, {
      method: "POST",
      headers: {"Content-Type":"application/octet-stream"},
      body: out
    });
  }
}

Each request includes the row number in the query string. The body of the request is raw binary RGB565 pixel data for that single row.

The ESP32 Upload Handler

On the ESP32 side, the async web server receives the binary upload. Since HTTP data can arrive in smaller chunks, the handler rebuilds the full 480 byte line before drawing it. 


void myDataUploadHandler(
    AsyncWebServerRequest* request,
    uint8_t* data,
    size_t len,
    size_t index,
    size_t total
) {
    if (!request->hasParam("y")) return;

    int y = request->getParam("y")->value().toInt();

    if (y < 0 || y >= 240) return;
    if (total != 480) return;

    static uint8_t lineBytes[480];

    if (index + len <= 480) {
        memcpy(lineBytes + index, data, len);
    }

    if (index + len == total) {
        drawLineFromBytes(y, lineBytes);
    }
}

The important values are:

  • data - the current chunk of received bytes
  • len - how many bytes arrived in this chunk
  • index - where this chunk belongs inside the upload
  • total - the full expected upload size

Drawing the Line

Once a full row has been received, the ESP32 converts the raw bytes back into 16-bit RGB565 pixels and draws a one-pixel-tall bitmap to the display. 


uint16_t lineBuf[240];

void drawLineFromBytes(int y, uint8_t* data) {
    for (int x = 0; x < 240; x++) {
        lineBuf[x] =
            ((uint16_t)data[x * 2] << 8) |
            data[x * 2 + 1];
    }

    tft.drawRGBBitmap(0, y, lineBuf, 240, 1);
}

That means the display is updated progressively from top to bottom as the browser sends each row. The ESP32 never needs to hold the full image in memory.

A complete 240×240 image would require over 115 KB of RAM, while this implementation only needs a 480 byte working buffer.

Handling Chunked HTTP Uploads

One thing I learned while building this project is that an HTTP upload isn't guaranteed to arrive all at once. A 480 byte scanline might arrive as several smaller packets: 


Chunk 1
128 bytes

Chunk 2
128 bytes

Chunk 3
128 bytes

Chunk 4
96 bytes

The web server callback provides the current offset and total size so the firmware can reconstruct the complete scanline before sending it to the display. Once the line has been drawn, the same buffer is reused for the next row.
