Writing a Serial Keyboard Wedge for Windows Part 2

By John Glatts

One thing that stuck with me from school was:
program to an interface, not an implementation.

That idea ended up being really useful when working on my SerialWedge project. A keyboard wedge sounds simple at first: read serial data, clean it up, and send it as keyboard input. But once you start supporting different devices, the problem gets more interesting.

A scale may send data one way. A barcode scanner may send it another way. A meter, gauge, caliper, or custom microcontroller may need completely different parsing logic. I did not want the main application to care about all of those details.

The goal was to keep the main wedge application simple, while allowing each device to define its own serial settings and data handling logic.

The SerialReaderBase API

In the Serial Keyboard Wedge, the interface is the API exposed through SerialReaderBase. This base class defines the common behavior that every serial reader needs to support.

The main application does not need to know if the data is coming from a scale, barcode reader, gauge, sensor, or some random box with an RS232 port. It only needs to know that there is a serial reader object that can start, stop, read data, and report incoming values back to the UI.

That gives the project a clean separation: 

Main Windows App
        |
        |-- SerialReaderBase
                |
                |-- DefaultSerialReader
                |-- MyDeviceSerialReader
                |-- MitutoyoSerialReader
                |-- OtherCustomDeviceReader

Each device-specific reader can override the parts that matter, while the rest of the program continues to work the same way.

Why This Helps

Without this structure, every new serial device would add more conditional logic to the main form. Eventually the code would turn into a pile of device-specific exceptions.

With SerialReaderBase, adding a new device is cleaner. I can create a new class, define the port settings, write the parsing logic, and plug it into the app. The UI does not need to be rewritten.

Device-Specific Serial Settings

One of the biggest headaches with serial devices is that the COM port settings have to match exactly. Baud rate, parity, data bits, stop bits, and handshaking all matter.

A custom serial reader can define its own default settings so the application starts in a known-good configuration for that device. 

public override PortSettings getPortSettings()
    {
        return new PortSettings("XOnXOff", 2400);
    }

That may not seem like a big deal, but it makes the tool much easier to test and reuse. Instead of remembering the correct settings every time, the reader class can load them for you.

The Worker Method

The core of each reader is the worker() method. This is where the serial data is read, cleaned up, parsed, and sent out as keyboard input. 

public override bool worker()
    {
        bool ret = true;

        try
        {
            string line = port.ReadLine();

            if (string.IsNullOrEmpty(line))
                return false;

            line = line.Replace("?", "");

            SendKeys.SendWait(line);

            updateCallback?.Invoke(line);
        }
        catch (TimeoutException)
        {
            ret = false;
        }

        return ret;
    }

This is the part that makes the wedge useful. The device can send whatever weird serial format it wants, and the reader can turn that into clean keyboard input for Excel, Notepad, an ERP system, or any other Windows application.

Adding a New Reader

To support a new device, I only need to create a new class that inherits from SerialReaderBase. 

class MyDeviceSerialReader : SerialReaderBase
    {
        public MyDeviceSerialReader(SerialPort port, UpdateCallback callback)
            : base(port, callback)
        {
        }

        public override void initPort()
        {
            port.Parity = Parity.Even;
            port.DataBits = 8;
            port.StopBits = StopBits.One;
            port.DtrEnable = true;
            port.RtsEnable = false;
        }

        public override bool worker()
        {
            // Read and process device-specific serial data here
            return true;
        }
    }

Then the main form can instantiate that reader instead of the default one. 

serialReader = new MyDeviceSerialReader(port, updateLiveInput);

That is the nice part. The device-specific behavior is isolated, but the rest of the wedge still works the same way.

Final Thought

This project started as a simple Windows utility, but the architecture matters. Industrial serial devices are all a little different, and pretending they all behave the same usually leads to messy code.

By building the wedge around SerialReaderBase, the application stays flexible. The main app handles the Windows side, and each reader handles the device side.

That makes it much easier to support new hardware without rewriting the whole tool.
