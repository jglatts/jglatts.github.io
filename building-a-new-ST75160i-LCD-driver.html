Building a New ST75160i LCD Driver

By John Glatts

In a previous post, I covered the process of debugging a newer revision of the NHD-C160100DiZ-FSW-FBW LCD from Newhaven Display. What initially looked like a simple display replacement turned into a much deeper investigation after I discovered that the newer module had transitioned from the ST7528i controller to the ST75160i.

Getting the display to ACK over I2C and show recognizable pixels was only half the battle.

The next step was building a proper driver.

Moving Beyond Bring-Up

Once the display was responding reliably, I started working through the controller datasheet and implementing the functionality needed for a usable graphics library.

At this point the hardware issues were mostly solved:

  • I2C communication was stable
  • The display was resetting correctly
  • The initialization sequence was working
  • The LCD glass and contrast circuitry were functioning

The challenge shifted from hardware debugging to understanding how the controller actually stores and displays pixels.

Understanding the Framebuffer

One of the biggest differences between the ST7528i and ST75160i controllers is how display memory is organized.

The ST75160i packs groups of vertical pixels into individual bytes of RAM. That means drawing a single pixel is not as simple as writing to an X,Y coordinate. The driver must determine which byte contains the target pixel, modify the correct bit, and then update the framebuffer.

Understanding the memory architecture was the key to making the display render correctly.

Once the framebuffer layout matched the controller's memory organization, graphics finally started behaving correctly.

Lines appeared where they were supposed to. Boxes looked like boxes. Text became readable.

Fixing Display Orientation

After getting pixels onto the screen, the next challenge was orientation.

The display initially appeared mirrored and upside down. This is a common issue when bringing up a new LCD controller because the controller's memory layout does not always match the physical orientation of the display glass.

Fixing the issue required adjusting the coordinate mapping and addressing logic inside the driver. Once the X and Y calculations matched the LCD layout, everything finally lined up as expected.

Building Graphics and Text Functions

With pixel rendering working correctly, I started adding higher-level graphics functions.

This included:

  • Pixel operations
  • Lines and rectangles
  • Bitmap rendering
  • Character drawing
  • Font support

Character rendering was particularly interesting because it required translating font data stored in flash memory into the framebuffer format expected by the controller.

Seeing the first correctly rendered text on the display felt like a major milestone.

Creating a Demo Application

A driver never really feels finished until it runs something useful.

To validate the implementation, I created a small demonstration application that displays text, graphics, and simple animations.

The display is connected using one of our FlexibleTest FFC interposers, allowing quick connection and disconnection during development and testing.

The demo became a convenient way to verify:

  • Driver stability
  • Graphics rendering
  • Font rendering
  • Interposer reliability
  • Overall system performance
This ended up being a great example of hardware and firmware development working together to validate a complete system.

Lessons Learned

Projects like this are a reminder that embedded development still rewards understanding the fundamentals.

The final driver was not built by guessing or copying code from the internet. It came from reading the datasheet, testing assumptions, and understanding how the controller actually works.

Along the way I gained a deeper understanding of:

  • I2C communication
  • LCD controller initialization
  • Display memory organization
  • Framebuffer design
  • Font rendering
  • Coordinate mapping

Most importantly, I walked away with a driver that I understand from the datasheet up.

Final Result

What started as a simple LCD migration ended up becoming a complete driver development project.

The ST75160i display is now rendering graphics and text correctly, running through demonstration screens, and operating through our FlexibleTest FFC interposer setup.

Sometimes the most valuable engineering projects start with a display that simply refuses to work.
