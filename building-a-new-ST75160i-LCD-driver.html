Debugging an ST75160i LCD Migration

By John Glatts

Building a New ST75160i LCD Driver

By John Glatts

After debugging the newer revision of the NHD-C160100DiZ-FSW-FBW LCD from Newhaven Display, I ended up writing a new driver for the ST75160i controller.

This started as a simple display migration. It turned into a really good low-level firmware project.

Why a New Driver Was Needed

The older display revision used an ST7528i controller. The newer module uses an ST75160i.

The displays look very similar, but the controllers are not firmware-compatible. The initialization sequence, RAM layout, addressing, and pixel packing all needed to be handled differently.

Same-looking LCD module. Different controller. Different driver.

Getting the Display to Respond

The first step was getting clean communication over I2C. A proper hardware reset pulse was required before the display would reliably ACK. 

digitalWrite(rst, LOW);
delay(20);

digitalWrite(rst, HIGH);
delay(200);

I also moved away from 5V logic during testing. The ESP32 ended up being a much better fit since the display expects 3.3V logic levels.

Writing Pixels Correctly

The biggest challenge was understanding how the ST75160i stores pixels in display RAM. This controller packs vertical groups of pixels into each byte. 

0x80 = row 0
0x40 = row 1
0x20 = row 2
0x10 = row 3

Once the framebuffer matched the controller's memory format, the display started behaving correctly. Lines, borders, and text finally rendered where they were supposed to.

Orientation Fixes

After the pixels were working, the next issue was orientation. The display was upside down and mirrored at first.

Fixing that required adjusting the coordinate mapping in the driver. Once the X and Y logic matched the physical LCD layout, the display finally felt usable.

Adding a Demo

After the basic graphics were working, I added a small demo to show the display running through our FlexibleTest FFC interposer setup.

The demo displays names, simple graphics, and animated test screens. It is a fun way to show that the driver, display, and interposer connection are all working together.

This was a great example of using a real product demo to validate both the hardware interface and the firmware.

What I Learned

This project was a good reminder that datasheets matter. A lot.

Writing the driver forced me to understand:

  • I2C communication timing
  • LCD reset behavior
  • Controller initialization
  • Framebuffer packing
  • Pixel addressing
  • Display orientation

It was also a nice reminder that the fundamentals still matter. Reading the datasheet, testing one thing at a time, and verifying each layer made the difference.

Final Result

The new ST75160i driver is now working. Pixels render correctly, text is readable, and the display runs through the demo cleanly.

This was a small project on the surface, but it ended up being a really useful embedded systems exercise. It also made the final demo feel a lot better because the driver is now something I actually understand from the datasheet up.
