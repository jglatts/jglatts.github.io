Replacing a VBA ERP with a Django-Based System

By John Glatts

I have been running a small ERP system built in Microsoft Access and VBA for years.

It worked. It tracked orders, generated reports, and handled day-to-day operations. But like a lot of tools in manufacturing, it grew organically and started to show its age.

The goal was not to build a “perfect ERP.” The goal was to replace something that already worked with something more maintainable, more scalable, and easier to extend.

Why Move Away from Access

Access and VBA are incredibly productive for getting something running quickly. For a single user or small team, they can go a long way.

Over time, though, a few limitations become obvious: 

- Hard to manage multiple users reliably
- Difficult to version control
- UI becomes cluttered and inconsistent
- Integrations are limited
- Scaling beyond a few users gets risky

None of these are immediate deal-breakers. But they add friction as the system grows.

The New Approach

The replacement system is built using Django, with a simple Bootstrap front-end and PostgreSQL as the database. 

Django (backend)
PostgreSQL (database)
Bootstrap (UI)
OpenPyXL (Excel report generation)

The key idea is to keep things just as simple as the original system, but move the logic into something that is easier to maintain long-term.

Core Features

The first version focuses on the essentials: 

- Create and edit fixture orders
- Track status (design, production, inspection, shipped)
- Dashboard with active orders
- Basic metrics (monthly sales, YTD totals)
- Generate inspection reports from Excel templates

That mirrors the functionality of the original VBA system almost exactly.

Inspection Reports

One important requirement was keeping the existing inspection report format.

Instead of rewriting that logic from scratch, the new system uses an Excel template and fills it programmatically. 

Load Excel template
Fill key cells with order data
Return file to user

This keeps the output consistent while simplifying the code significantly.

What Changed (and What Didn’t)

The workflow is still very familiar: 

Create order → Track progress → Generate report

But the way it is implemented is different: 

Access forms → Web UI
VBA logic → Python (Django)
Local file → Database-backed system

The biggest improvement is that multiple users can now interact with the system at the same time without worrying about file locking or corruption.

Running It Internally

The system runs on an internal office PC and is accessed through a browser. 

http://office-pc:8000

It is not exposed to the internet. Access is limited to the internal network or VPN.

This keeps things simple and secure without needing a full production deployment.

What I Like About This Approach

It keeps the spirit of the original system.

The goal was not to reinvent everything. It was to take a working workflow and put it on a better foundation.

Good internal tools are not about features. They are about reducing friction in everyday work.

Next Steps

There is still a lot that can be added: 

- User accounts and permissions
- Inline editing (faster updates)
- File path integration (drawings, reports)
- Better reporting and analytics
- Audit logging

But even at this stage, the system is already usable.

Final Thoughts

Rewriting internal tools can feel risky, especially when the existing system “works.”

The key is to move incrementally: 

Replicate → Improve → Extend

That approach keeps things grounded and avoids overengineering.
